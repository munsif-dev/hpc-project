\begin{abstract}
We implement and evaluate six variants of the training loop for a compact
multi-layer perceptron (MLP) that predicts per-residue secondary structure
($\mathrm{Q}_3$) on the CB513 benchmark: a serial baseline, two shared-memory
parallelisations (OpenMP and POSIX threads), a distributed-memory
implementation with MPI, a hybrid MPI $+$ OpenMP version, and a CUDA
implementation that offloads the whole training loop to the GPU. All
variants share the same model code, the same CLI, and the same data split so
that accuracy can be compared directly. The serial baseline reaches
test $\mathrm{Q}_3 = 62.74\,\%$ and acts as the reference target for every
parallel variant. We measure per-epoch wall-clock time as a function of
shared-memory thread count, MPI rank count, hybrid rank/thread layout, and
CUDA batch size, then discuss where each design scales well and where it
plateaus. The final tables and figures in this report are generated from
the JSON logs written by the binaries, not from manually typed timing
values.
\end{abstract}

\section{Introduction and Motivation}\label{sec:intro}

Protein secondary-structure prediction assigns each residue of a protein
sequence to one of three classes: $\alpha$-helix~(H), $\beta$-sheet~(E), or
coil~(C). It is an enabling step for downstream tertiary-structure analysis
and drug design, and the classical approach is to train a neural network
over a sliding window of residues centred on the target
residue~\cite{rost1993,zhong2007}. Zhong~et~al.~\cite{zhong2007} showed on
early multi-core Intel hardware that the training of such a network
parallelises well using OpenMP or POSIX threads, obtaining speedups close
to the core count. In this project we repeat that experiment on modern
hardware \emph{and} extend the parallelisation strategies to distributed
memory (MPI), a hybrid shared/distributed scheme, and GPU acceleration
(CUDA).

The project deliverables, as specified in the course
guideline~\cite{guideline}, are: (1)~serial code, (2)~shared-memory
programming code, (3)~distributed-memory programming code, (4)~hybrid
programming code, and (5)~an analysis report that (a)~includes a diagram
and a description of how parallel programming concepts are applied,
(b)~compares accuracy of the parallel implementations against the serial
reference, and (c)~measures timing of the serial and parallel coding by
varying the number of threads and other parameters. This document fulfils
requirement~(5). CUDA is beyond the minimum requirement but is included to
exercise every parallel technology mentioned in the technology-usage list
of the guideline.

\section{Dataset and Preprocessing}\label{sec:data}

We use the CB513 benchmark of Cuff \& Barton~\cite{cuff1999}, a curated
set of $513$ non-homologous protein domains (${\sim}84\,000$~residues). The
processing pipeline lives in \texttt{scripts/} and is deterministic under a
fixed seed:

\begin{enumerate}[noitemsep,topsep=2pt]
  \item \textbf{Download} (\texttt{download\_cb513.sh}) --- fetches the
        canonical distribution tarball.
  \item \textbf{Parse} --- extracts \texttt{(protein\_id, residue,
        8-state-label)} tuples from the raw \texttt{.all} files.
  \item \textbf{8$\to$3 collapse} (matching Zhong~et~al.\ §4):
        \(H,G,I \to H\); \(B,E \to E\); everything else $\to C$.
  \item \textbf{Sliding window} of size~$13$ with flat-edge padding,
        one-hot encoded over the $20$ amino-acid classes, giving an
        input vector of dimension \(20 \times 13 = 260\).
  \item \textbf{Split} --- fixed 70/15/15 train/validation/test (indices
        persisted to \texttt{data/processed/cb513/splits/fixed\_split.json}).
  \item \textbf{Binary persistence} --- the final tensors are serialised
        under \texttt{data/processed/cb513/binary/} for fast loading.
\end{enumerate}

Final sample counts are summarised in Table~\ref{tab:data}. The class
distribution is approximately $33\%\,H$ / $22\%\,E$ / $45\%\,C$ across every
split, consistent with published statistics for CB513.

\section{Serial Model and the \texorpdfstring{$\mathrm{Q}_3$}{Q3} Metric}
\label{sec:serial}

The model is a two-hidden-layer MLP:
\[
  \text{Input}(260)\to\text{Dense}(H_1)\to\text{ReLU}
  \to\text{Dense}(H_2)\to\text{ReLU}\to\text{Dense}(3)\to\text{Softmax}.
\]
Loss is cross-entropy fused with softmax for a numerically stable
backward pass:
\[
  \frac{\partial L}{\partial z_3} = p - \mathbf{1}_{y_{\text{true}}},
\]
where $p=\mathrm{softmax}(z_3)$ and $\mathbf{1}_{y}$ is the one-hot
encoding of the true label. Optimisation uses mini-batch SGD with an
optional step-decay learning rate. The reference configuration used for
every comparison run is
\begin{center}
  \(H_1=256\), \(H_2=128\), \(\mathrm{epochs}=80\), \(\mathrm{batch}=64\),
  \(\mathrm{lr}=0.01\), \(\mathrm{seed}=42\).
\end{center}

The $\mathrm{Q}_3$ metric, following Eq.~(19) of Zhong~et~al., is
\begin{equation}\label{eq:q3}
  \mathrm{Q}_3 \;=\;
  \frac{N^{\text{correct}}_H + N^{\text{correct}}_E + N^{\text{correct}}_C}%
       {N_{\text{total}}} \times 100\,\%.
\end{equation}

On the reference run (single CPU worker, GCC with \texttt{-O3
-march=native}) the serial baseline achieves
\[
  \boxed{\text{test}\ \mathrm{Q}_3 = 62.74\,\%} \qquad
  \text{total training time}\approx 441\,\mathrm{s}.
\]
All parallel variants are validated against this reference.

\section{Parallel Designs}\label{sec:designs}

Every variant reuses the model code in \texttt{src/models/mlp.c} unchanged.
The variants differ only in how the mini-batch is partitioned among
workers and how their per-worker gradients are combined before the SGD
update. A single rule holds across all designs:

\begin{quote}
\textit{Model weights are \textbf{read-only} during the parallel region.
Each worker accumulates gradients into a \textbf{private} buffer; a
reduction sums these; a single SGD update is then applied. This removes
all locking on the weight matrices.}
\end{quote}

\subsection{OpenMP}\label{sec:openmp}

The OpenMP variant (\texttt{src/openmp/train.c}) pre-allocates one
\texttt{MLPGrad} plus per-sample scratch (\texttt{a1, a2, logits, probs})
per thread and reuses them every batch. The batch loop is wrapped in
\verb|#pragma omp parallel| and \verb|#pragma omp for schedule(static)|
partitions the batch samples contiguously across threads. Loss is
aggregated with \verb|reduction(+:batch_loss)|. After the parallel region
the master serially reduces per-thread gradients into thread~0's buffer
and calls \texttt{mlp\_sgd\_update} once.

\subsection{POSIX Threads}\label{sec:pthreads}

The pthreads variant (\texttt{src/pthreads/train.c}) uses a
\textbf{persistent master/worker pool} created once at program start and
reused for every mini-batch, which avoids the per-batch
\texttt{pthread\_create} / \texttt{pthread\_join} cost that the original
Zhong paper already identified as prohibitive. Synchronisation is
two-barrier: \texttt{bar\_start} releases the workers for the current
batch, and \texttt{bar\_done} lets the master wait until every worker has
finished its slice. Each worker owns a pre-allocated \texttt{MLPGrad} and
scratch; the partitioning inside a batch is contiguous, matching OpenMP's
\texttt{schedule(static)}.

\subsection{MPI (Distributed Memory)}\label{sec:mpi}

The MPI variant (\texttt{src/mpi/train.c}) runs the same algorithm across
\emph{multiple physical machines}. All ranks load the full dataset and
initialise an identical model; because \texttt{mlp\_init} is
deterministic under \texttt{--seed}, no explicit weight broadcast is
needed. All ranks execute the same shuffle each epoch (same seed), so
they agree on the order of samples.

Per mini-batch, rank~$r$ out of $R$ processes a contiguous slice
\([r\cdot\mathrm{chunk},\,(r{+}1)\cdot\mathrm{chunk})\) of the batch and
accumulates into a \emph{rank-local} gradient. The six gradient arrays are
backed by a \textbf{single contiguous flat buffer} (layout:
$\mathrm{dW}_1, \mathrm{db}_1, \mathrm{dW}_2, \mathrm{db}_2, \mathrm{dW}_3,
\mathrm{db}_3$), so one
\verb|MPI_Allreduce(MPI_IN_PLACE, ..., MPI_SUM)| handles the whole
gradient state in a single collective --- six separate collective calls
would pay latency six times. After the Allreduce every rank applies the
same \texttt{mlp\_sgd\_update}, keeping the models bit-identically
synchronised. Validation, test inference, and JSON logging happen only on
rank~0.

\subsection{Hybrid MPI + OpenMP}\label{sec:hybrid}

The hybrid variant (\texttt{src/hybrid/train.c}) combines both layers of
parallelism:

\begin{itemize}[noitemsep,topsep=2pt]
  \item \textbf{Outer (MPI)} --- identical to Section~\ref{sec:mpi}:
  ranks split the mini-batch across machines and combine their partial
  gradients with \texttt{MPI\_Allreduce}.
  \item \textbf{Inner (OpenMP)} --- inside each rank, the rank's slice is
  further split across OpenMP threads using the same per-thread
  \texttt{MLPGrad} pattern as Section~\ref{sec:openmp}. The intra-rank
  reduction is performed before the cross-rank Allreduce.
\end{itemize}

\noindent We initialise MPI with
\verb|MPI_Init_thread(MPI_THREAD_FUNNELED)| --- only the main thread makes
MPI calls, and indeed all our MPI collectives are \emph{outside} OpenMP
regions. The oversubscription rule is
\(\mathrm{ranks}\times\mathrm{threads} \le \mathrm{cores}\) per machine, and
we pin with \verb|OMP_PROC_BIND=true OMP_PLACES=cores|.

\subsection{CUDA}\label{sec:cuda}

The CUDA variant (\texttt{src/cuda/train.cu}) keeps the entire training
loop on the GPU. The design decisions are:

\begin{itemize}[noitemsep,topsep=2pt]
  \item \textbf{Data resident on device.} Full train/val/test tensors and
  the shuffled index list are uploaded once; per-batch cost is only a
  small \texttt{cudaMemcpy} of the batch-index slice.
  \item \textbf{Column-major throughout} --- cuBLAS native; a single
  gather kernel builds a column-major batch matrix from the row-major
  device copy using the index slice, avoiding a global transpose.
  \item \textbf{cuBLAS \texttt{sgemm} for every GEMM} --- forward
  $W\cdot X$, gradient $\mathrm{d}W = \mathrm{d}Z\cdot A^\top$, and
  back-propagation $\mathrm{d}A = W^\top \mathrm{d}Z$.
  \item \textbf{Fused gradient + SGD step.} Instead of materialising
  explicit gradient buffers on the device, we call the
  gradient-producing \texttt{sgemm} with
  \(\alpha = -\mathrm{lr}/B\) and \(\beta=1\), which lets the GEMM write
  directly into the weight matrix. Bias updates use \texttt{sgemv}
  against a vector of ones with the same scaling.
  \item \textbf{Custom kernels} handle the three element-wise ops:
  \texttt{bias\_relu\_kernel} (bias-add followed by ReLU),
  \texttt{relu\_mask\_kernel} (ReLU derivative on the back-propagated
  gradient), and a fused \texttt{softmax\_xent\_grad\_kernel} which, per
  batch column, applies $b_3$, computes numerically stable softmax,
  accumulates the cross-entropy loss via \texttt{atomicAdd}, and
  converts $Z_3$ in place to $\mathrm{d}Z_3 = p - \mathbf{1}_y$.
  \item \textbf{Validation / test Q3} reuses the existing host
  \texttt{mlp\_predict} after copying weights back from device to host.
\end{itemize}

\section{Experimental Setup}\label{sec:setup}

\paragraph{Execution host.} The final experiment host is the HPC desktop:
Intel Core~i9-14900K, 24 physical cores / 32 logical CPUs, one NUMA node,
Ubuntu Linux, GCC~15.2, and \texttt{-O3 -march=native}. This machine is
used for serial, OpenMP, Pthreads, single-node MPI, and hybrid
MPI+OpenMP runs.

\paragraph{MPI mode.} MPI is executed locally with multiple ranks on the
same HPC host. This still exercises the distributed-memory programming
model --- each rank owns a private address space and communicates only via
MPI collectives --- while avoiding the unstable multi-laptop network path.
The multi-laptop runbook remains in \texttt{scripts/cluster\_setup.md} as
an optional extension if a true multi-node demonstration is required.

\paragraph{GPU host.} CUDA is run on the same HPC machine when launched
from a shell that can access \texttt{/dev/nvidia*}. The detected GPU is an
NVIDIA GeForce RTX~5090 with 32~GB VRAM, driver~595.71.05, and CUDA
runtime support reported by \texttt{nvidia-smi}. The installed compiler is
\texttt{nvcc}~12.4 and cuBLAS is linked by the \texttt{train\_cuda}
target. Exact versions are captured in
\texttt{results/environment/HPC\_ENVIRONMENT.txt} and
\texttt{results/cuda/ENVIRONMENT.txt}.

\paragraph{Fairness controls.}
\begin{itemize}[noitemsep,topsep=2pt]
  \item Same \texttt{--seed 42} for every run $\Rightarrow$ identical
        initial weights and per-epoch shuffle order.
  \item Same hyperparameters
        ($H_1=256$, $H_2=128$, $\mathrm{lr}=0.01$,
        $\mathrm{batch}=64$).
  \item Same 70/15/15 split.
  \item \texttt{OMP\_PROC\_BIND=true OMP\_PLACES=cores} for every
        shared-memory run.
  \item Timing excludes data loading and final evaluation; it covers
        only the epoch loop.
\end{itemize}

\paragraph{Measurement protocol.}
\begin{itemize}[noitemsep,topsep=2pt]
  \item \textbf{Accuracy table} --- full 80-epoch run per variant at the
        reference configuration. CPU variants must stay within
        $\pm0.5$ percentage points of serial test $\mathrm{Q}_3$; CUDA is
        accepted within $\pm1.0$ point because GPU reduction order differs.
  \item \textbf{Timing sweep} --- 20-epoch run per configuration, repeated
        three times. The reported timing value is the mean of the per-epoch
        \texttt{epoch\_time\_s} values in the JSON log, with standard
        deviation across repeated runs.
\end{itemize}

\subsection{Shared-memory scaling: OpenMP vs Pthreads}\label{sec:shmem}

Figure~\ref{fig:time_vs_threads} reports the per-epoch wall-clock time and
Figure~\ref{fig:speedup_vs_threads} the resulting speedup relative to the
single-threaded run of the same variant.

\begin{figure}[H]
  \centering
  \begin{subfigure}[b]{0.48\textwidth}
    \includegraphics[width=\linewidth]{time_vs_threads.png}
    \caption{time per epoch}\label{fig:time_vs_threads}
  \end{subfigure}
  \hfill
  \begin{subfigure}[b]{0.48\textwidth}
    \includegraphics[width=\linewidth]{speedup_vs_threads.png}
    \caption{speedup}\label{fig:speedup_vs_threads}
  \end{subfigure}
  \caption{Shared-memory scaling. Both variants use the same mini-batch
  data-parallel reduction scheme; the shape of the curve therefore
  reflects the hardware, not the API.}
\end{figure}

We observe:
\begin{itemize}[noitemsep,topsep=2pt]
  \item \textbf{Near-linear scaling up to the count of P-cores} (first
  several doublings of the thread count).
  \item \textbf{Sub-linear regime after P-cores are saturated} --- E-cores
  contribute, but at lower IPC than P-cores, so the slope of the
  speedup curve flattens.
  \item \textbf{Sharp diminishing returns on SMT} going from 8 to 16
  threads: two threads per physical core compete for the same execution
  units and L1/L2, and the per-sample work
  (one forward + backward through a $260\to256\to128\to3$ MLP) is already
  fast enough that the per-batch reduction cost starts to dominate.
  \item \textbf{OpenMP vs Pthreads:} both reach similar throughput at
  steady state because they implement the same reduction strategy. OpenMP
  benefits from a cached parallel team at low thread counts; Pthreads
  catches up once the batch size per thread is large enough to amortise
  barrier latency.
\end{itemize}

\subsection{Distributed-memory scaling: MPI}\label{sec:mpires}

Figure~\ref{fig:mpi_ranks} shows the per-epoch time for local MPI rank
counts on the HPC host. The accuracy at every rank count is identical
(to within the float tolerance in
Section~\ref{sec:acc}) because the $\mathrm{Allreduce(SUM)}$ reproduces
the single-rank gradient exactly.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.6\textwidth]{time_vs_ranks_mpi.png}
  \caption{MPI training time per epoch on the HPC host, using separate
  MPI address spaces and \texttt{Allreduce} communication.}
  \label{fig:mpi_ranks}
\end{figure}

Per-rank compute drops approximately~$1/R$, but the network cost of the
per-batch \texttt{Allreduce} on the packed gradient buffer
($\sim$\,250\,kfloats) is fixed. The crossover at which the network cost
dominates the compute saving is a function of
\(\mathrm{batch\_size}\) and the ratio
$T_{\text{compute}}/T_{\text{net}}$.

\subsection{Hybrid MPI + OpenMP}\label{sec:hybres}

Figure~\ref{fig:hybrid} reports the hybrid configuration sweep on the HPC
host. The tested layouts include
\(1{\times}1,1{\times}8,1{\times}16,1{\times}24,2{\times}4,2{\times}8,
4{\times}4,4{\times}8,8{\times}2,8{\times}4\), all constrained by
\(R\cdot T\le32\). The design motivation is that
\texttt{MPI\_Allreduce} is not used inside a node --- that work is
off-loaded to OpenMP's thread-local reduction --- so only inter-node
gradient exchange pays the network cost.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.7\textwidth]{hybrid_heatmap.png}
  \caption{Hybrid per-epoch time over the local \((R,T)\) matrix.}
  \label{fig:hybrid}
\end{figure}

For a fixed total worker count \(R \cdot T\), keeping \(R\) small and
\(T\) large should win when the LAN is the bottleneck; swapping the ratio
wins when per-node cache pressure is the bottleneck.

\subsection{GPU: CUDA}\label{sec:gpures}

Figure~\ref{fig:cudares} plots per-epoch time against mini-batch size on
the RTX~5090.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.6\textwidth]{cuda_time_vs_batch.png}
  \caption{CUDA training time per epoch vs mini-batch size.}
  \label{fig:cudares}
\end{figure}

Per-epoch time is expected to decrease with increasing batch size up to
the point where the GPU becomes occupancy-bound, then flatten. Because
our model is small, the kernel-launch overhead and the per-batch
host$\to$device copy of the index list are the most likely next
bottleneck once GEMM efficiency saturates.

\section{Discussion}\label{sec:discussion}

\subsection{Where scaling works well}

\emph{Mini-batch-level data parallelism} is the natural primitive. It
maps identically to OpenMP, Pthreads, MPI, and CUDA --- each worker
processes a sample and accumulates into a private gradient. This gave us
almost-the-same algorithm and accuracy across six implementations.
Making the model weights read-only during the parallel region (and only
reducing the gradient) removes all weight-matrix locking, which is the
single most important simplification in the design.

\subsection{Where scaling plateaus}

\begin{itemize}[noitemsep,topsep=2pt]
  \item \textbf{Small model, small per-sample work.} One forward +
  backward pass through a $260{\to}256{\to}128{\to}3$ MLP is cheap. As we
  add threads, the fixed reduction cost
  (\(\Theta(|\mathrm{params}|)\approx 250\,\mathrm{kfloats}\) per batch)
  consumes a growing share.
  \item \textbf{Mixed CPU topology and SMT.} On the i9-14900K, scaling
  changes as runs move from performance cores to efficiency cores and then
  to SMT siblings. SMT threads share execution units and caches with
  their physical twin, so the final scaling step is naturally sub-linear.
  \item \textbf{MPI \texttt{Allreduce} on LAN.} With
  \(\sim\,250\,\mathrm{kfloat}\times4\,\mathrm{B} = 1\,\mathrm{MB}\) per
  Allreduce, and several hundred batches per epoch, cumulative traffic is
  large on a gigabit link. We mitigated this by packing all six gradient
  arrays into one flat buffer (one Allreduce per batch instead of six).
  Further reduction would require gradient accumulation across batches
  (changing the optimisation semantics) or overlap of Allreduce with the
  next batch's forward pass.
\end{itemize}

\subsection{Why OpenMP and Pthreads can differ}

Both implementations use the \emph{same} data-parallel reduction scheme,
so at steady state they converge to near-identical throughput. Any
differences come from \textbf{runtime overhead}:

\begin{itemize}[noitemsep,topsep=2pt]
  \item OpenMP keeps a thread team alive across parallel regions: a
  recurring \verb|#pragma omp parallel| reuses the same workers.
  \item Our Pthreads implementation is \emph{also} a persistent pool with
  barrier-based dispatch --- that was a deliberate design choice to
  avoid the per-batch fork/join cost that the original Zhong paper
  identifies as prohibitive. A naive \texttt{pthread\_create} per batch
  is orders of magnitude slower.
  \item At very low thread counts (1--2) the OpenMP runtime's first-touch
  memory placement tends to be slightly better, giving OpenMP a small
  edge. At higher thread counts the gap closes and either variant's
  overhead is dwarfed by the reduction cost.
\end{itemize}

\subsection{Practical limits from our hardware}

\begin{itemize}[noitemsep,topsep=2pt]
  \item The MPI results are single-node multi-rank results. They validate
  the distributed-memory code path, but do not include real network
  latency between physical machines.
  \item The CPU has mixed performance and efficiency cores. Scaling curves
  should therefore be interpreted by core class: moving from P-cores to
  E-cores and then to SMT threads naturally changes the slope.
  \item CUDA must be launched from a shell that can see
  \texttt{/dev/nvidia*}. Sandboxed shells may fail even when the host
  terminal's \texttt{nvidia-smi} works.
\end{itemize}

%%======================================================================
\section{Conclusion and Future Work}\label{sec:conclusion}

We implemented six data-parallel training variants of a CB513
$\mathrm{Q}_3$ predictor using a shared model kernel and a unified CLI.
The final experiment workflow validates each variant against the serial
baseline, then measures time-per-epoch scaling by changing only the
parallelism knob: thread count for OpenMP/Pthreads, rank count for MPI,
rank-thread layout for Hybrid, and batch size for CUDA. Shared-memory
variants are expected to scale until core or memory bandwidth saturation;
MPI and Hybrid are limited by the packed-gradient \texttt{Allreduce}; and
CUDA should benefit most as batch size grows enough to amortise kernel
launch overhead.

Future improvements identified during the project but out of its scope:

\begin{itemize}[noitemsep,topsep=2pt]
  \item Overlap \texttt{MPI\_Allreduce} with the next batch's forward
  pass (\emph{communication / computation overlap}) --- largest expected
  benefit for the MPI and hybrid variants.
  \item Replace the per-batch full Allreduce with a Ring-Allreduce /
  Tree-Allreduce from libraries such as NCCL or RCCL (GPU clusters).
  \item Mixed-precision (fp16) on the GPU: model is small enough for
  precision margin.
  \item PSSM-based features (as in Zhong et al.) instead of pure
  one-hot --- orthogonal to parallelism but expected to lift the
  absolute $\mathrm{Q}_3$ from 62.7\,\% into the 70\,+\,\% range reported
  in the paper.
\end{itemize}

\section{Reproducibility}\label{app:repro}

\paragraph{Compile commands.} The root \texttt{Makefile} has one target
per variant:
\begin{lstlisting}
make train_serial           # gcc -O3 -march=native
make train_omp              # gcc -O3 -march=native -fopenmp
make train_pthreads         # gcc -O3 -march=native -pthread
make train_mpi              # mpicc
make train_hybrid           # mpicc + -fopenmp
make train_cuda             # nvcc + -lcublas
\end{lstlisting}

\paragraph{Runtime commands.} The recommended way to reproduce all
experiments is the scripted workflow:
\begin{lstlisting}
bash scripts/run_hpc_experiments.sh smoke
bash scripts/run_hpc_experiments.sh timing-cpu
bash scripts/run_hpc_experiments.sh timing-cuda
bash scripts/run_hpc_experiments.sh accuracy
python3 scripts/make_plots.py
\end{lstlisting}

The underlying commands used by the script are:
\begin{lstlisting}
./train_serial     --epochs 80 --batch 64 --seed 42 --out results/serial
./train_omp        --epochs 80 --batch 64 --seed 42 --threads 16 --out results/openmp
./train_pthreads   --epochs 80 --batch 64 --seed 42 --threads 16 --out results/pthreads

mpirun -np 4 \
    ./train_mpi --epochs 80 --batch 64 --seed 42 --out results/mpi

OMP_PROC_BIND=true OMP_PLACES=cores \
mpirun -np 4 \
    ./train_hybrid --threads 4 --epochs 80 --batch 64 --seed 42 \
                   --out results/hybrid

./train_cuda       --epochs 80 --batch 64 --seed 42 --out results/cuda
\end{lstlisting}

\paragraph{Machine and software versions.} Per run, captured in
\texttt{results/<variant>/<run>.json} under the \texttt{hardware} key;
for the GPU, additionally in \texttt{results/cuda/ENVIRONMENT.txt}.

\paragraph{Data provenance.} See \texttt{docs/data\_provenance.md} for
exact URL, checksum, and download date of the CB513 distribution.

\paragraph{Workflow diagrams.}
Editable draw.io source is stored in
\texttt{docs/diagrams/hpc\_workflows.drawio}. The report also includes
TikZ versions of the main OpenMP, Pthreads, MPI, and CUDA workflows for
self-contained PDF generation.
